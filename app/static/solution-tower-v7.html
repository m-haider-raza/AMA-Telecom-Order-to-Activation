Solution scope and delivery requirements

This customer walkthrough describes the solution design and illustrative workflow. The running Azure reference implementation uses synthetic data and simulated carrier adapters. Türkiye residency requires supported Azure Local infrastructure at an approved Turkish site, local application services, inference, keys, logs and backups, and approved egress controls. Connected Arc platform metadata requires review; disconnected operation requires eligibility and capacity.

Business objectives describe the intended value, rather than a quantified customer outcome. TMF622/TMF641-inspired interfaces require customer-specific contracts and conformance acceptance. The trusted boundary sends real Azure Communication Services email. Customer status links require sign-in and order ownership; partner access is organisation-scoped. Unknown-fault escalation requires a service-desk integration and accountable operational owner.

Hosted Entra agent identities and runtime managed identities are distinct. Receiving APIs enforce caller identity, roles, operation allowlists and current policy; agents cannot write state or grant approvals directly. Staff token fallback has operator permissions, not a personal service-manager identity.

Named business sponsor and technical-owner assignments, access reviews and incident alerts are production operating-model requirements, not verified live assignments. Agent 365 catalog registration remains pending tenant approval; it does not replace the authorization controls already enforced.

Microsoft product icons identify their services. Operator branding supplies industry context; it implies no endorsement, relationship or actual carrier integration.
